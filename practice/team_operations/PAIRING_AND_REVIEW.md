# Pairing, onboarding and review capacity

This is an original suggested routine, not a validated training intervention. Adapt duration and limits to the work; none of the values below estimates a learning effect.

## First three encounters

1. **Observe and predict.** A newcomer reads the work order and one failing case. Before a mentor or agent acts, the newcomer predicts the result and names the authorized edit boundary. The mentor demonstrates one task and makes the evidence visible.
2. **Drive with review.** The newcomer controls the bounded task; the mentor asks for an explanation of the diff and expectation source. Declare when an assistant is allowed, preserve the first explanation and record specific feedback. A green rerun is completion evidence under those conditions.
3. **Apply elsewhere.** Use the short practice in this directory or an approved repository task with a different mechanism. Ask what facts must be checked before reusing the earlier procedure. Preserve the initial answer and revision. Do not call this a delayed-retention study or a professional competence certificate.

Before independent work, the responsible owner still reviews access, task scope and acceptance obligations. Learning progress does not grant release or incident authority. A newcomer should have a named person for uncertainty and a safe route to decline an inappropriate tool or unsupported claim.

## The queue, not the agent count, controls starts

List proposed, active, ready-for-review, blocked and disposed items, including reviewer work, maintenance and incidents. Assign a single accountable owner to the next action. Choose active and review-queue limits from actual capacity; the Treasury example's two/one values are illustrative.

When review is full, stop starting new implementation. Help reproduce an existing result, shrink a reviewable diff, resolve a missing source or pair with the reviewer. Do not waive a required check, disguise review as done, or assume an idle agent creates reviewer capacity. If a review cannot be staffed, defer the work or change the plan under its owner.

At the team review, inspect the oldest queued item and the reason it waits. Change the workflow or limit when evidence supports it and retain the reason. Avoid comparing individuals by tokens, generated lines or the number of parallel agents they supervise. Report task friction and review burden at the agreed use boundary.

## A disagreement that changes a decision

Question: the maker wants to merge a label change because the new snapshot test passes; the reviewer wants the boundary and payment-authority assertions.

Worked disposition: preserve the self-test, run the independent cases, and record which selected behavior they cover. If the review capacity is unavailable, keep the item waiting. The maker's confidence and the full queue do not replace the required decision. Feedback should describe the missing evidence rather than rank the person's worth.

Primary context: DORA's work-in-process guidance recommends visible work and capacity-based limits (https://dora.dev/capabilities/wip-limits/). This routine and its Treasury settings are new author-designed practice; no numeric limit or mentoring benefit is claimed from that source.
