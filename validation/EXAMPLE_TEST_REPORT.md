## Live native observation and its limits

The native stack was installed outside both repositories in sibling `esa_ai_native_runtime_01`. The model download verified all 2,497,280,256 bytes against the existing SHA-256 pin; the Ubuntu x86-64 archive also matched its size and hash. Neither the pre-existing Darwin b11429 server nor a different model was substituted.

The owned Linux x86-64 container used 6 GiB RAM and six CPUs under emulation. The server used context 16,384, q8_0 key/value caches, six threads, batch 256/microbatch 128, a 1,500-second maximum runtime and ten-second shutdown grace. These are recorded run settings, not certification of the historical environment or a minimum-resource guarantee. Initial client prompt processing was slow, around 10–13 tokens/second, despite the successful tiny inference.

OpenCode 1.19.3 made real model-selected read, write, edit and check calls. It first attempted to read missing documents, then created `spec.md` and `plan.md` and edited `api.py`. Its first selected-contract check passed three cases and failed four because `csv_formatter` was undefined. Its own subsequent edit introduced an `IndentationError`. The invocation reached `OUTER_TIMEOUT` after 900.056 seconds (child exit -15). The actual session was exported; only those three allowed files changed. No manual repair, retry or prompt tuning was used to convert this observation into a claimed success. This is a failed generated candidate, not a regression in the supplied reference solution, which passed its checks separately.

After the invocation stopped, separate contract, independent-review, CSV-demo and JSON-demo commands each exited 1 because the generated module could not be imported. The independent behavioral review could not complete or produce its usual review JSON; it is not counted as 17 executed checks. These reruns left the candidate unchanged. The server's shutdown and finish receipts were retained.

Cleanup completed: the model server exited cleanly with code 0 and the owned container was stopped; Docker reported no out-of-memory kill. The container's idle PID 1 exited 137 after the stop grace interval, separate from the already-stopped server. A durable copy of the native evidence is retained at `../esa_ai_native_runtime_01/validation_evidence/` relative to the repository root, with `SUMMARY.json` and `EVIDENCE_SHA256.json`; no model binaries or evidence packet were added to Git.

Direct SDK calls to the configured canonical MCP server passed valid, domain-refusal and schema-refusal controls. A declared nonsecret startup canary was readable (`READ_SUCCEEDED`): this does not establish an OS filesystem sandbox. These SDK calls were not model-selected calls from the coding host.

## Apple Silicon timeout follow-up

The subsequent retry resolved the observed inference timeout, but did not produce an accepted CSV implementation. The earlier Linux observation above remains unchanged.

The same verified Qwen weights and llama.cpp b11799 release were reused with the separately verified Darwin ARM64 archive and native OpenCode 1.19.3. Both [launchers](../practice/native_client/README.md) now accept explicit `--server-binary` and `--n-gpu-layers` overrides; the default CPU recipe is unchanged. Receipts record host architecture, executable path/hash and actual argv. The guide provides the native Metal command.

A controlled cold benchmark used identical 3,404-token prompts, zero cached tokens, 32 output tokens, seed 42/temperature 0, context 16,384, q8_0 K/V, six threads and batch 256/microbatch 128, with separate fresh servers:

| Native Darwin backend | Prompt processing | Total request |
| --- | --- | --- |
| CPU, GPU layers 0 | 91.998 s; 37.00 tokens/s | 94.485 s |
| Metal, GPU layers 99 | 4.795 s; 709.91 tokens/s | 5.375 s |

Metal prompt processing was about 19.2 times faster in this single matched sample. Earlier emulated Linux prompt processing was around 10–13 tokens/s, but was not the same synthetic benchmark. These observations identify emulated CPU inference as the practical bottleneck; they are not general hardware performance guarantees.

The fresh task retained the original prompt except its project path, identical starter hashes and the 900-second task deadline. It completed in 39.952 seconds instead of timing out, but generated an `IndentationError`. Two separately labeled failure-guided continuations were then preserved: guided01 took 21.568 seconds and fixed syntax but left an undefined helper (3/7 contract and 7/17 independent cases passed); guided02 took 51.420 seconds and left the required API function absent. All four final independent commands exited 1 before behavioral cases could run, and no review JSON was produced. Guided02 explicitly allowed reading the selection module; write scope was unchanged. No reference solution or manual candidate repair was supplied. Client exit 0 is not task acceptance. No further retries were made and none of these candidates was incorporated.

The d8 server stopped cleanly with exit 0. The snapshotted original launcher also passed native health and a bounded tiny inference request, then stopped with exit 0 on SIGTERM. Both servers were cleaned up.

The retry exposed a receipt-unit issue: Darwin reports `ru_maxrss` in bytes, unlike Linux KiB. Updated launchers retain the raw value and unit and normalize the KiB field. Historical retry receipts retain their original mislabeled raw-byte field and must not be interpreted as KiB. Launchers used for live observations were snapshotted before this correction. Regression tests failed before the correction and all 17 validation tests subsequently passed on macOS and Linux; this includes explicit binary/GPU arguments, metadata, preflight failures and bounded shutdown.

Raw retry evidence, original candidate snapshots, session exports, benchmark inputs and launcher snapshots are under `/private/tmp/esa-ai-validation.iB0c1O/native/darwin_retry/`. Downloads remain outside Git in the sibling `esa_ai_native_runtime_darwin_01` directory. This is a separately recorded Darwin observation, not a reproduction of the historical Ubuntu environment.

The durable retry packet is retained outside Git at `../esa_ai_native_runtime_darwin_01/validation_evidence_retry/` relative to the repository root, including `SUMMARY.json` and its evidence hash inventory. The final fixes were mirrored into the official checkout: all 17 validation tests pass there, doctor reports no protected/starter findings, changed Python files have no editor diagnostics, and `git diff --check` is clean. Nothing was committed or pushed.

## Reproduce the main local checks

From the repository root, using Python 3.12 and a suitable Git:

```bash
python3.12 -m venv ../esa_ai_test_env
. ../esa_ai_test_env/bin/activate
python -m pip install -r practice/verification_tools/requirements.txt -r practice/mcp_cli/requirements.lock
python -m pip check
export TMPDIR=/private/tmp  # macOS; use /tmp on Linux
export PYTHONDONTWRITEBYTECODE=1
python -B reader_start.py doctor
python -B reader_side/tools/run_checks.py --output "$TMPDIR/esa-core-results.json"
python -B -m unittest discover -s reader_side/extended_tests -v
python -B -m unittest discover -s practice/orchestration -p 'test_*.py' -v
python -B -m unittest discover -s practice/sdd -p 'test_*.py' -v
python -B -m unittest discover -s practice/workflow_cost -p 'test_*.py' -v
python -B -m unittest discover -s practice/harness_engineering/tests -v
python -B -m unittest discover -s practice/mcp_cli -p 'test_*.py' -v
python -B -m unittest discover -s validation -p 'test_*.py' -v
```

Use new, canonical output destinations for example runners (on macOS, `/private/tmp/...`, not its `/tmp` alias). Follow the individual [practice guides](../practice/README.md) for positive examples and expected negative controls. Keep the source tree unchanged during the core suite: entry tests deliberately detect concurrent edits.

Raw local evidence for this audit is under `/private/tmp/esa-ai-validation.iB0c1O/`: `core/` (including Linux results and extra entry/specimen branches), `official-core-results.json`, `practice/SUMMARY.json`, `practice/commands.json`, `sdd-framework/SUMMARY.json`, `native/` (including `live/` runtime limits, configured runs, server lifecycle and failed CSV attempt), `harness/REPORT.json`, `upstream/REPORT.json`, `upstream-k1/REPORT.json`, `upstream-k4/REPORT.json`, `verification/OBSERVATIONS.json` and `mcp/COMPARISON.json`. These local temporary outputs are not a portable published artifact and may be removed by the operating system; this report records their scoped outcomes. Runtime downloads and their verification receipts remain in the sibling native-runtime directory, outside Git.

## Not established by this audit

- Successful autonomous CSV repair was not established: the initial bounded live client attempt failed; the later fresh run passed with explicit guidance, as recorded above. A functioning installation is not a guarantee that a small model produces correct code. Supplied starter defects remain intentional; neither a generated candidate nor a worked answer was promoted into the starter.
- Live SDD model generation, model-selected coding-host MCP integration, provider credentials, external permissions enforcement and model-backed harness research remain separate external trials. Installed framework scaffolds and successful SDK transport do not establish generated requirements fidelity, coding-host tool selection or OS sandboxing.
- Real human learning, delayed transfer, independent reader acceptance, team field economics and production release remain unobserved; synthetic rehearsals do not satisfy them.
- Historical source snapshots, unsafe examples and archived toolchain probes were not indiscriminately executed as applications. Syntax compilation is not runtime certification, and this audit does not certify other Python versions or Windows.
