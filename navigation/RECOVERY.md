# Choose a starting state and recover safely

Run `python3 -B reader_start.py doctor` and `python3 -B reader_start.py show N` from
the companion. The card describes the supplied state; it does not inspect and
accept every current candidate. Dedicated gates establish the narrower facts
named in their receipts.

## First visit

From the unchanged delivered companion, run:

```bash
python3 -B reader_start.py new 1 --destination ../my_treasury_lab
```

This copies the complete lab and installs only Chapter 1's known faulty router.
Enter the new directory, read its Chapter 1 card and make the repair. After its
review, preserve your router and receipt and adopt the inherited reference
router exactly as the main README explains. Continue Chapters 2–14 in that
same copy, capturing a separate before-edit baseline for each chapter.

## Enter in the middle

`new N --destination ../study_N` creates a separate study copy of the delivered
starters. It does not install earlier solutions or mark prerequisites complete.
Read the card's prerequisite first. For an independent study, use its explicit
worked-example route. For cumulative candidate readiness, complete the earlier
candidates in your existing copy and use the candidate route. A reference
receipt cannot be submitted as evidence for a different working copy.

## A stale receipt

1. Retain the failing receipt and compare its named inputs with your current
   files. A comment, configuration or reviewed-artifact change can matter even
   when a selected behavioral test still passes.
2. Decide whether the change belongs to the current chapter. Restore an
   accidental change from your retained copy, or return to the responsible
   chapter and review it there. Do not recapture a before-edit baseline to hide
   an out-of-scope edit.
3. Rerun the affected gates and create a new rehearsal/receipt in an unused
   directory. Preserve the old result and explain why it is superseded. Rebind
   dependent CP12, CP13 and CP14 sessions to their actual parent identity.
4. Keep human decisions separate. A refreshed machine receipt does not resolve
   pending requirements, architecture and copy decisions, owner reconciliation or release approval.

## Start again

Keep the existing copy with its evidence. Extract the release into another new
directory and run `new` there. The entry command never overwrites an existing
destination and refuses a modified starter. This is a non-destructive reset,
not a filesystem sandbox or a restore command for a production service.

## Choose the Chapter 7 practice copy

Keep the cumulative planning exercise in your existing study copy. Its candidate
plan can be repaired without granting the pending architecture decision. The
controller practice uses separate snapshots and output directories; read its
permissions, retry budget and stopping rules before dispatch.

The Treasury harness experiment has a different starting requirement: extract
the same edition into a new directory and run the command from that untouched
edition's `companion/`. Its five source pins include both the router and
`repo/engineering/planning/delegation_plan.json`. A valid earlier router or plan
repair can therefore cause a source-pin refusal in the cumulative copy. Preserve
that copy and its evidence; do not replace the repaired file, edit a pin, or
recapture the baseline to make the experiment run.

For the pinned upstream Harness2 demo, select Python 3.12 or 3.13 before running
its command. The core lab's Python floor is not that demo's supported range.
Use a new output directory for each practice run. Neither optional exercise
settles the original CP07 human decision. See `CHAPTER_ROUTES.md` for the entry
and return points.

## Continue from team practice to Chapter 14

After Chapter 13's agreement, pairing and experiment discussion, go directly to
Chapter 14's concepts, dashboard and cost worksheets if those are your goal.
Those reading and worksheet activities do not require a CP13 session.

For the cumulative executable Chapter 14 lab, retain matching synthetic CP12
incident and CP13 transfer sessions. `python3 -B reader_start.py show 14` lists the
candidate prerequisites and a complete worked-example command chain. The
worked-example route stays separate from acceptance of your current candidates.
The ordinary synthetic chain requires no 24-hour wait. The separate delayed
human pilot has its own participant, timing and independent-review requirements;
it is not a prerequisite for the ordinary lab.

The protected checker is controlled by the reader/teacher. Its hashes detect
changes against that baseline; a learner must not rewrite them to obtain a
passing result. Current author maintenance is recorded in the complete author package under
`revision_d4/`; the standalone companion preserves the protected current baseline
and historical receipts without turning those receipts into current acceptance.
