2.6 Follow one bounded task in an installed client
The files, tools and rules become easier to understand when we watch them work to-
gether. We will return to the familiar Chapter 1 defect in a fresh copy: reject malformed,
nonfinite and nonpositive amounts while preserving the public API, BR-001/v1 and the
EUR 5,000 boundary. Using a known small problem lets us concentrate on the client
rather than learning another domain at the same time. Preserve your cumulative work-
ing copy; this optional observation has its own disposable copy and return point.
The primary route uses the installed OpenCode 1.19.3 client with Qwen3-4B
Q4_K_M served locally by llama.cpp b11799.

model, offers tools and applies its application permission rules. The model proposes
actions; the client executes an allowed action and returns its result to the model. The

Step 1: establish what the client is being asked to repair
Open the intent before starting the client.
For this task, a zero amount is invalid
even though it is below EUR 5,000. A malformed decimal should produce the specified
rejection rather than an exception. These facts come from the approved teaching intent,
not from whatever change the model finds easiest to generate. The initial acceptance
run gives the model a concrete failing observation and gives the reviewer a baseline.
The companion setup records the unchanged companion location in ESA_COMPANION
and defines three separate working locations: ESA_RUNTIME holds the installed client
and model, ESA_WORK is a new Chapter 1 study copy, and ESA_PACKET retains evidence
outside that copy. After setup, run the following from the unchanged companion root:

and zero cases return the wrong route; the malformed and nonfinite cases raise excep-

The preparation step retains the starting file bytes, while the scope baseline identifies
the router as the sole source that may change.

Concept: A baseline explains what a later result means
A baseline records the state before an intervention. Here it answers two practical
questions: which defect did the client receive, and which files were permitted to
change? A later passing test report without that starting state cannot show whether
the client repaired the intended problem, began with a worked answer or changed
the expectations. A file hash identifies bytes; it does not decide whether those
bytes express the right requirement.
Step 2: inspect effective permissions before making a model request
The companion’s practice/native_client/configure_chapter1.py prepares a
configuration and a task prompt for the actual location of your copy. It checks the
starter and baseline, detects the Git worktree used for permission paths, and refuses to
overwrite an earlier preparation. It does not invoke the model. The prompt supplies
exact absolute paths to the intent, tests, router, initial result and repository guidance.
It asks for the bounded repair, one named acceptance command and a stop for human
review.
cd "$ESA_COMPANION"
python3 -B practice/native_client/configure_chapter1.py \
--work "$ESA_WORK" --runtime-root "$ESA_RUNTIME" \
--output "$ESA_PACKET/configuration"
Read the generated configuration before using it. Only those named study files may
be read through the native read tool. Only the router may be edited. The command
allowance names the exact acceptance invocation and its new output file; other com-
mands are denied. The recorder’s task declaration separately names the source and
report that may change. That declaration supports a later comparison; it is not an OS
permission setting.
The retained setup exposed a useful versioning failure.
The current documentation

the same narrow command rule. The reader recipe therefore captures the installed ver-
sion, effective configuration and effective agent before it offers a task to the model. A
successful parse is only the first check.

Read the rule as well as the tool name
The observed effective agent enabled read, edit, write and bash.
Those

Step 3: use the observed failure to choose the next action
After inspecting the preparation, invoke the actual client through the generated com-
mand specification. The model, context, output and step limits are declared in that
specification and its configuration. They bound the exercise; they do not guarantee
that the model will repair the function.
python3 -B validation/observe_native.py capture \
--spec "$ESA_PACKET/configuration/CLIENT_TASK.json" \
--output "$ESA_PACKET/attempt_01"
Read the native tool events before deciding what to do next. A failed file read, an
unfinished model request and a rejected candidate need different corrections. Changing
the code cannot fix a path that the client was never permitted to read. Granting more
file access cannot make an invalid decimal comparison correct. The retained episode
makes these distinctions concrete.

Worked example: Three different results after a client stops
Process completion is established by the exit status and any timeout. Task com-
pletion requires the actual reads, edits, checks and candidate. Acceptance requires
the independent review and decision. The historical d6 first attempt completed the
process with exit zero while leaving the task unfinished. Later, a final-looking fail-
ure message was followed by automatic context compaction in the host. Neither a
reassuring exit code nor a concluding sentence supplies the other observations.
Keep each prompt, configuration and failed result under its own attempt name. When an
intervention supplies API-level guidance or starts a fresh session, record that assistance:
the result then reflects those more specific instructions.
A failed request without a
completed usage receipt has unknown token use, and an application field containing
cost: 0 does not measure total financial cost. Chapter 14 will make this accounting
distinction explicit.

Step 4: retain the native record and review the candidate
The command recorder preserves stdout, stderr, literal arguments and before/after file
inventories. The native session export supplies the client’s own message and tool context.
Use the companion’s direct-file export recipe, then parse the JSON and verify the session
identifier. A command returning zero does not establish that its complete output was
retained. The guide preserves the collection failure that motivated this check.
After the agent stops, the reader reruns the seven acceptance cases into a new report,
checks the original edit baseline and compares the candidate with the preserved starter.
A green result means that those cases passed against the identified candidate. The diff
still needs review against the intent: did the validation preserve the threshold, return
type and policy version? The companion guide gives the commands and retains the
initial sources, native events, unsuccessful attempts and independent results together
under practice/native_client/observed/ch01_01/.

Step 5: connect the policy lookup with a smaller tool set
The next task needs information rather than a code change. The client should retrieve
BR-001/v2, request the unknown identifier BR-999/v1, and attempt one deliberately
wrong argument type. We use the existing SDK server and catalogue from the earlier
MCP example. Reading v2 makes its contents visible; it does not authorize replacing
the Chapter 1 rule with that later policy.
The companion’s practice/native_client/configure_mcp.py prepares a separate
study and evidence directory, the actual host configuration and the exact prompt. It
uses the pinned Python environment and the existing wire recorder. Only the policy
lookup is offered to the model; no file-editing or shell tool is needed for this task. The
preparation creates files but does not invoke a model or start the server. Inspect it
before running the generated client task. A fresh preparation is needed for each launch
because the wire recorder preserves its first trace rather than overwriting it.
Follow three different boundaries in the resulting record. First, the host must start the
process and discover its tool. Second, a native model action must select the tool and
supply arguments. Third, the server must return the actual catalogue result or refusal.
A well-formed unknown identifier is a domain outcome: the tool understood the request
but found no such policy. A list where the schema requires a string is an argument error.
If the host rejects that call before sending an MCP request, the evidence must name
that layer rather than attributing the rejection to the server.
The retained 22 October native run makes these distinctions concrete. OpenCode 1.19.3
started the canonical server with MCP SDK 2.3.0, negotiated protocol 2025-11-25, dis-
covered lookup_policy and selected it in the model’s native tool events. BR-001/v2
returned the catalogue record; BR-999/v1 returned UNKNOWN_POLICY. The attempted
wrong-type call is a useful failed claim: although the prompt requested an empty array,
the native event and wire both contain the string "[". The server therefore returned
another domain refusal. The model’s first final response claimed that schema valida-
tion rejected an array. We preserve that response and reject its explanation against the
actual request and result. The available evidence does not isolate whether the intended
array changed in the model, provider adapter or client parsing.

Concept: A read-only tool can run in a process with wider rights
The lookup accepts fixed policy identifiers and exposes no file-reading or writing
operation. Its Python process nevertheless runs with the rights granted by its launch
environment. The optional observation declares one harmless canary file outside
both the study and server directories, then instruments the serving interpreter to
try reading that file at startup. This is a canary: deliberately placed test data with
no secret value, used to observe a specific boundary.
A successful read establishes access to that path by that process at that time.
It does not show that the model can request arbitrary files through the policy
tool. A missing probe record leaves the read unobserved. The probe changes the
runtime through an explicit startup hook while leaving the canonical server source
unchanged; it does not test network access, secret inheritance, external writes or
isolation established later.
The startup probe also produced a positive result in this run: the canonical serving
interpreter read the declared 50-byte harmless canary outside the study directory before
initialization. The retained probe identifies that process, path and content hash. It
establishes that particular startup read. It supplies no evidence of post-initialization
containment, network restrictions or a model-accessible arbitrary-file operation.
Inspect the native events beside the raw MCP messages, and inspect the process probe
separately. A tool label, a successful lookup and an operating-system restriction are
three different observations. The same care applies to protocol versions: record the
actual opening exchange rather than deriving it from an installed package’s version
number. The earlier SDK-only trace remains evidence about that earlier connection.
The complete native collection guide retains each connection’s configuration and its
own resulting messages under practice/native_client/observed/mcp_host_01/.
