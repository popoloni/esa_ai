4.5 Run the same Treasury task through two artifact journeys
A structure check can answer questions such as: does a proposal file exist, and does a
requirement have a scenario section? A behavioral comparison asks a different question:
does the described answer agree with the source rule for the cases that matter? Imag-
ine two documents both containing a below-threshold example but neither mentioning
equality. Their headings can be complete while their examples leave the same ambiguity
unresolved.

4.5.1 Separate what the CLI did from what the author supplied
The recorded primary setup uses Spec Kit 1.2.2; the contrast uses OpenSpec 1.14.1.
Both initialize their Codex integration in isolated local directories. The releases and
package hashes are recorded with the run, and the commands complete without a
coding-agent client or model session [35, 56]. Installing an integration’s skill files does
not demonstrate that the client discovered or followed them.
Spec Kit’s bundled helpers create an empty feature-spec template and plan template,
then return a task template. OpenSpec creates change metadata and reports the depen-
dencies among proposal, specification, design and tasks. These are actual CLI results,
preserved under the exercise’s evidence/ directory. The populated Treasury documents
are separately labelled author_exercise: they were written for this comparison, not
generated by those agent skills. The original setup failures and successful retries are
retained too; the evidence does not pretend that installation was frictionless.
The primary authored set contains a feature spec, candidate plan and blocked task list.
The contrasting set contains a change proposal, an added explanation-capability spec,
candidate design and the same task obligations. Compare where the reason for the
change, unchanged behavior, observable cases and pending decision are visible. Differ-
ences in file organization can help a team review its work; they do not by themselves
establish a quality or productivity winner.
