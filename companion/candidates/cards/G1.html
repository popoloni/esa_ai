G1 proposal cards

G1-P01

The persistence boundary is the public record, so I kept storage layout behind that interface. A row identifier locates a JSON representation of the five request fields; each read reconstructs a new mapping with the identifier added. This makes an alternative physical layout possible while keeping callers unchanged. Please judge the returned fields and the process-boundary observation together.

Artifact: reserve: the write transaction after constructing payload and opening the connection.

try:
    cursor = connection.execute(
        "INSERT INTO bookings_v2 (payload) VALUES (?)",
                                (json.dumps(payload),))
    identifier = cursor.lastrowid
    connection.commit()
finally:
    connection.close()
return Outcome(201, "confirmed", identifier)

G1-P02

The three public operations share a path-keyed record registry. Initialization establishes the database location, and writes make the complete record immediately available to subsequent lookups. That arrangement keeps the first increment small and avoids introducing a larger persistence abstraction. The local scenarios exercise creation and retrieval through the public functions; the same interface remains available for the next increment.

Artifact: The module registry and reserve; get_reservation reads this same registry.

_records = {}
def reserve(path, **request):
    identifier = len(_records.setdefault(str(path), {})) + 1
    _records[str(path)][identifier] = {"reservation_id":
        identifier, **request}
    return Outcome(201, "confirmed", identifier)

G1-P03

I separated an empty lookup from unavailable storage at the connection boundary. The read opens an existing database and lets storage errors reach its caller; an initialized store can still report that the requested identifier is absent. The URI construction also needs scrutiny for filenames containing reserved characters. No initialization or recovery step is hidden inside this read.
