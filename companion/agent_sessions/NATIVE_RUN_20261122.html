What the run found and what changed

G3 to G4: a lineage layout that no contract named. This lineage’s G3 kept its reservations in a table named reservations_v3, with the native column list. OPS-G4/v3 names reservations and two reservations_v2 layouts, so the first G4 worker implemented those three, refused this one and asked for an owner mapping, which is the contracted behaviour. The protected check could not pass: four methods failed because the corruption fixture builds only named layouts. The 16 November run met the same class of problem and answered it by writing OPS-G4/v3 for its own table. A reader whose agent picks any other name had no documented way forward.

The companion now handles this at advance G4. When the retained G3 creates a layout that OPS-G4/v3 does not name, advance writes the owner decision G4-OD-01 for that lineage alone (docs/G4-OD-01.md and docs/G4-SCHEMA-MAP.json), provided every column uses a name the named layouts already give to the same role. Otherwise it refuses and explains how to supply a mapping with --schema-map, which it checks against the columns init_db creates. The contract, the tests and their count are unchanged; the fixture and the reference observer read the mapping when it exists. G4 was re-advanced from the same accepted G3 integration. The second worker read the decision, implemented the mapping generically, probed a wrong signature and a competing pair itself, and passed 13/13 and the handoff. The first attempt is retained as work/g4-before-owner-mapping and work/g4-agent-before-owner-mapping.

Receipts: a used name could not be superseded. The operator ran the printed G2 check once before the agent, which consumed g2-first.json; the ledger then read that failing receipt, although the agent’s candidate passed 17/17. The ledger now reads numbered retries of every printed receipt (g2-first-02.json, …) and gates on the most recently recorded one, listing earlier ones as superseded. The CLI’s refusal names the next free retry. G2 and G4 gate on their -02 receipts.

verify_curriculum.py adds a deterministic control: a G3 lineage built from the reference by renaming its table goes through integration and advance G4; an observer that ignores the mapping fails four methods; the reference passes the handoff; three malformed or unnecessary operator maps are refused.

Limits

One run per stage shows that the lineage gap occurs, not how often. Codex CLI was not available here. No human operator, reader trial or human acceptance is represented.
