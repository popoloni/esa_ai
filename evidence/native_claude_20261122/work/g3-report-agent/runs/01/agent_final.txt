**What `build_report` does**
- It calls `booking.get_reservation`. If that returns nothing, it returns `{"found": False, "reservation": None, "current": None}`.
- Otherwise it calls `booking.reservation_status` and returns `found: True`, the record as stored, and `current` with only `state` and `version`.
- It contains no SQL, no `init_db`, no writes and no exception handling, so a missing database raises `sqlite3.OperationalError` and nothing is created.
- The two reads are separate calls, so the result is not a single concurrent snapshot, as the contract says.

**Observations**
- I added one case the contract doesn't cover. If a record exists but its status read then returns nothing, `build_report` raises `RuntimeError` instead of inventing a state. This can't happen in the current booking API, since deletion isn't supported. Say if you would rather it behave differently.
- The A component test has no fake dependencies. It uses the real `booking` API on temporary SQLite files.

**Integration assumptions for the operator**
- `reservation_cli.py` (Contribution B) will import `reservation_report.build_report` and call it with `(path, reservation_id)`.
