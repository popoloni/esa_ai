The cancellation increment for RES-002/v1 is implemented, and the 7 supplied tests in `tests/test_g3.py` now pass (they all failed before). I changed only `booking.py` and `DOSSIER.md`. Human acceptance is still PENDING, and I did not run protected acceptance or continuation.

**Acceptance example.** Member-1 reserves asset A for 09:00–10:00 and gets id 1 at version 1.
- `cancel(..., "member-1", 1)` returns 200 `cancelled` at version 2.
- Repeating with version 1 returns 409 `stale-version`. Repeating with version 2 returns 200 `already-cancelled` at version 2.
- Member-2 can now reserve the same slot (201).
- Replaying member-1's original request returns id 1 as a replay, and the status stays `cancelled`.

**What changed in `booking.py`**
- **Schema:** the new table is `reservations_v3`, with `state` and `version` columns, and `user_version` is now 3. Older tables are kept untouched.
- **Migration:** G2 rows become `active` at version 1 with the same IDs and the same six public fields. Running `init_db` again does nothing.
- **Status and cancel:** `reservation_status` returns `{state, version}` or `None`. `cancel` runs in one `BEGIN IMMEDIATE` transaction and applies the checks in the order 404, 403, 409. Those three outcomes change nothing.
- **Cancelled slots:** the conflict check only counts `active` rows, so a cancelled interval no longer blocks a new reservation. The idempotency lookup ignores state, so a replay can never revive a cancelled row.
