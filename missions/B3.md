A schema upgrade does not itself approve a new business rule. An activated policy
does not rewrite the policy attached to a historical decision. The new history
API accepts an `amount_eur` string and a bounded ASCII `beneficiary_id`. Amount
text uses ASCII digits, up to twelve integer digits, up to two fractional digits
and an optional minus sign, with no leading plus. Leading zeros are allowed
within the twelve-digit integer limit and disappear during canonicalization.
Use whole-input `fullmatch` and ASCII `[0-9]`; a final newline is not ignored.
B1-API/v2 allows a plus and 32 total characters, so a valid router input can still
be refused at this narrower ledger boundary. This explicit persistence boundary is separate from
the inherited router's API. Keep the rule stated in the contract; do not infer
it from a convenient parser.

`PolicyStore(path, catalog)` owns the store. Its main operations are:

| Operation | Meaning |
|:---|:---|
| `decide(id, payload)` | Create once, or return the stored decision for the same identity and canonical payload |
| `activate(version)` | Select the default policy for later new decisions |
| `replay(id)` | Return the stored evidence without recomputation |
| `recompute(id)` | Calculate against the recorded policy snapshot and compare without creating a decision |
| `reevaluate(old_id, new_id, version)` | Make a new decision with an explicit policy and parent link |

## 2. Delegate: identity must outlive the ambient default

The approved identity is the request ID plus a canonical payload comparison.
It excludes the currently active policy. Numeric spellings such as `4000.0` and
`4000.00` identify the same amount for retry, while the originally submitted field
values remain stored in canonical JSON. The API receives a dictionary, so it
does not claim to retain transport bytes it never received. Legacy migration has
a separate obligation to preserve its supplied historical JSON strings.

A same-ID retry after activation returns the exact stored v1 record without a
new decision or audit row. Different payload or an explicit incompatible policy
under that identity raises `IDEMPOTENCY_CONFLICT` without mutation. Explicit
reevaluation needs a new ID and a parent pointing to the old request. It may have
a different route while leaving the old record intact.

The supplied history machinery also computes digests, checks recorded policy snapshots
and restricts updates/deletes through immutable-history triggers. Those mechanisms
help detect or prevent specific changes through this store. They do not turn a
local SQLite file into independently authenticated historical truth. Source
provenance and control of the stored state remain part of the trust boundary.
