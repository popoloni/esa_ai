Table: The expanded reservation observations.

Situation Required result and effect
A valid, available interval 201/confirmed; one committed reservation
Same member and key, same asset and interval 200/confirmed, original identifier, replayed=True
Same member and key, different payload 409/idempotency-key-reused; no replacement
New request overlaps the same asset 409/interval-conflict; no reservation created
Adjacent intervals or a different asset Independent valid reservations may succeed
Invalid identifier, timestamp or interval Corresponding distinct 422 result; no reservation created

Intervals are half-open. Timestamps use exact UTC seconds, YYYY-MM-DDTHH:MM:SSZ; duration is positive and at most 24 hours. Identifiers are nonempty strings of at most 128 characters. Canonical timestamps support chronological string comparison; arbitrary date text would break that assumption.

Before delegating, specify lathe-2, 13:00–14:00 on 16 May 2025; an adjacent 14:00–15:00 request; and reuse of the original member/key with its end changed to 15:00. State the distinguishing result and what existing state must survive.

G2-P01

Retries should not allocate another reservation. This proposal recognizes the prior operation early and returns its existing identifier, keeping the original row untouched. The common successful-retry path is consequently short, and later conflict checks can concentrate on new operations. The review should consider both repeated delivery and callers that reuse an identifier while revising their request.

Artifact: reserve: the selected identity and its replay branch.

prior = con.execute("""
            SELECT id, request_key FROM reservations
            WHERE member_id = ? AND request_key = ?
        """, (trusted_member_id, idempotency_key)).fetchone()
if prior is not None:
    con.execute('COMMIT')
    if prior[1] == idempotency_key:
        return Outcome(
            200, 'confirmed', prior[0], replayed=True
        )
    return Outcome(409, 'idempotency-key-reused')

G2-P02

A coordinator planning several weeks needs an actionable schedule even when some requested dates are occupied. This helper collects the available dates and omits conflicting ones, so the offered schedule can still contain useful appointments. The existing single-reservation API remains intact. The proposed series operation presents that partial set as the dates to book for the request.

Artifact: The proposed new series API; existing single-reservation behavior is unchanged.

def plan_recurring(slots, is_available):
    """Proposed series planner; returns the dates it would
    book.
    """
    return [slot for slot in slots if is_available(slot)]

G2-P03

Migration is a compatibility operation with a clear rollback boundary. The conversion carries the approved representations into the current schema, preserving identifiers and public values, and leaves the source rows available for explanation. Ambiguous identities and invalid old commitments stop the conversion. Reinitialization and replay of an imported request are useful checks on whether that preservation is complete.

Artifact: init_db: selected row-conversion statements inside the migration loop, then exception cleanup; identifier, member, asset, start, end and key come from the legacy row.

4. Decide: retain a compatible increment

python3 companion/start.py continue G2 \
  --candidate work/g2 \
  --output work/evidence/g2-handoff.json

Continuation migrates a historical reservation, retries its identity, challenges changed content and creates an adjacent reservation. Its database and continuation.json remain in work/evidence/g2-handoff/; the receipt identifies candidate, expectations, actual commands and artifact hashes.
