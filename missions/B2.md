# B2. Bound the provider and preserve attribution {#mission-b2}

**Session planning target:** setup 10 min · implementation 30 min · review and handoff 20 min (60 min total).

Delegate a bounded intake adapter around your repaired Treasury router.
There are two distinct actors: **your coding agent** reads, edits and checks
`intake.py`; the product's injected **Provider** is a scripted local fixture.
The latter classifies valid requests as `MATCH` or `REVIEW`; it is not the
agent implementing the adapter. Invalid amounts are rejected locally.

A transient provider failure consumes an attempt; a response must belong to
its request. Your result classifies requests without authorizing payment.
The product fixture needs no network or paid provider. The live coding route
uses the separately configured client described in the companion.

Each request supplies `request_id` and `amount_eur`. The injected provider takes
those two values and returns exactly `{"request_id": ..., "classification": ...}`.
Its classification is either `MATCH` or `REVIEW`. The local router's outcome and
the provider's classification are distinct fields. Neither field is a payment
approval, and the combined result keeps `payment_authorized=False`.

Write an example before coding. A batch contains an invalid negative amount,
a valid item whose first provider call is unavailable, and two more valid items.
With a total budget of three calls, decide which calls may occur, what the final
item should report when the budget is exhausted, and what evidence a reviewer
needs to attribute the response to its request. Count the failed attempt in the
budget.

INTAKE/v1 distinguishes three ordinary record states. `REJECTED` means local
validation prevented a provider call. `CLASSIFIED` means a valid, matching response
was received. `DEFERRED` means the allowed work ended without such a response.
Deferral is not a successful classification, and the implementation must not fill
it with a default `MATCH` to keep the batch looking complete.

## 2. Delegate: retries are part of the contract

Only `ProviderUnavailable` is retryable. An unexpected exception remains visible.
A response with another request's identity, an unknown classification or a different
field set raises `ProviderProtocolError`. Preserve request identity across every
retry and report each attempt's number and outcome. Duplicate request IDs in one
batch are caller errors: validate the entire batch before any provider call.
A duplicate therefore raises `ValueError` with `calls=0`, not after partial work.
Errors retain their original type and expose `receipt`, `attempts`, `records`
and `calls`. Keep preceding successes and the final `INVALID_RESPONSE` or
`PROVIDER_ERROR` attempt. A raised exception must not erase consumed calls or
make their later cost accounting disappear.

The limits have different scopes. `max_attempts` bounds each request; `max_calls`
bounds the whole batch. A per-request loop can still overspend the batch budget if
it resets the total count for every item. Conversely, checking the total only after
a call permits one call beyond the approved limit. Derive your boundary examples
from those two observations.

### B2-P01

The batch loop tries to finish an item already in progress after a transient provider interruption. It preserves the request identifier and records every invocation so the caller can see the effort spent before the batch returns. The completion path is designed to avoid abandoning useful work at the edge of an allowance. Review that path against both the item-level and batch-level budgets.

*Artifact: evaluate_batch: the budget guard before the next provider invocation.*

```python
if len(attempts) > max_calls:
    break
event = {"request_id": key, "attempt": attempt}
attempts.append(event)
```

### B2-P02

A classification is usable only when its response belongs to the submitted request and has the agreed shape. The adapter checks that relationship before adding a completed record. It distinguishes the retryable provider condition from other failures and retains the attempt evidence on exceptions. Invocation bounds and response validity remain separate decisions in the loop.

*Artifact: evaluate_batch: response validation after recording the current attempt; exceptions retain the receipt.*

```python
if (
    not isinstance(response, dict)
    or set(response) != {
        "request_id", "classification"}
    or response["request_id"] != key
    or not isinstance(
        response["classification"], str)
    or response["classification"] not in (
        "MATCH", "REVIEW")
):
    event["outcome"] = "INVALID_RESPONSE"
    raise ProviderProtocolError(
        "response identity or schema does not match"
    )
event["outcome"] = response["classification"]
```

### B2-P03

Duplicate detection belongs before the first provider effect. This proposal examines the entire submitted batch before entering the existing bounded loop, so a late duplicate cannot invalidate work after calls have already occurred. It addresses identity within this batch only. A later process retry still needs the durable identity contract introduced in the history mission.

*Artifact: Preflight helper called before the provider loop; error snapshots are attached by evaluate_batch.*

```python
def _unique_requests(requests):
    rows = list(requests)
    ids = [row["request_id"] for row in rows]
    if len(ids) != len(set(ids)):
        raise ValueError("duplicate request_id in this batch")
    return rows
requests = _unique_requests(requests)
```
