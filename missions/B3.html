B3. Preserve a decision when policy changes

Run commands from the package root. Live-client setup and current status · Offline recorded tours

Session planning target: setup 10 min · implementation 40 min · review and handoff 25 min (75 min total).

Treasury lowers its routing threshold from EUR 5,000 to EUR 3,000. A request that previously entered the standard queue would now require human review. At the same time, a caller retries the old request after losing its response. Should the system return the old decision, recompute it, or create a new evaluation?

Delegate a persistent decision history that preserves those meanings through restart and migration. The coding agent must inspect your retained dependencies and the incomplete ledger before choosing a repair. These synthetic decisions authorize neither payment nor production migration.

Separate these version axes in your dossier:

Axis Current meaning
HISTORY-API/v1 Accepted payload, identity and operation semantics
Database schema 2 Representation of policy versions, decisions, settings and audit events
BR-001/v1 Finite-positive routing with threshold 5000.00
BR-001/v2 Finite-positive routing with threshold 3000.00

A schema upgrade does not itself approve a new business rule. An activated policy does not rewrite the policy attached to a historical decision. The new history API accepts an amount_eur string and a bounded ASCII beneficiary_id. Amount text uses ASCII digits, up to twelve integer digits, up to two fractional digits and an optional minus sign, with no leading plus. Leading zeros are allowed within the twelve-digit integer limit and disappear during canonicalization. Use whole-input fullmatch and ASCII [0-9]; a final newline is not ignored. B1-API/v2 allows a plus and 32 total characters, so a valid router input can still be refused at this narrower ledger boundary. This explicit persistence boundary is separate from the inherited router’s API. Keep the rule stated in the contract; do not infer it from a convenient parser.

PolicyStore(path, catalog) owns the store. Its main operations are:

Operation Meaning
decide(id, payload) Create once, or return the stored decision for the same identity and canonical payload
activate(version) Select the default policy for later new decisions
replay(id) Return the stored evidence without recomputation
recompute(id) Calculate against the recorded policy snapshot and compare without creating a decision
reevaluate(old_id, new_id, version) Make a new decision with an explicit policy and parent link

Before coding, write an event sequence with amount 4000.0: create under v1, activate v2, retry the same ID as 4000.00, attempt different content under that ID, recompute the original, and explicitly reevaluate under a new ID. Predict both the returned policy and the number of decision/audit rows after each step.

2. Delegate: identity must outlive the ambient default

The approved identity is the request ID plus a canonical payload comparison. It excludes the currently active policy. Numeric spellings such as 4000.0 and 4000.00 identify the same amount for retry, while the originally submitted field values remain stored in canonical JSON. The API receives a dictionary, so it does not claim to retain transport bytes it never received. Legacy migration has a separate obligation to preserve its supplied historical JSON strings.

A same-ID retry after activation returns the exact stored v1 record without a new decision or audit row. Different payload or an explicit incompatible policy under that identity raises IDEMPOTENCY_CONFLICT without mutation. Explicit reevaluation needs a new ID and a parent pointing to the old request. It may have a different route while leaving the old record intact.

The supplied history machinery also computes digests, checks recorded policy snapshots and restricts updates/deletes through immutable-history triggers. Those mechanisms help detect or prevent specific changes through this store. They do not turn a local SQLite file into independently authenticated historical truth. Source provenance and control of the stored state remain part of the trust boundary.

Migration deserves its own decision. The supplied synthetic v1 fixture contains historical payload, policy and outcome, plus a provenance record binding the source ID and row digest. migrate_legacy(path, catalog, provenance) must validate those inputs before completing conversion, preserve the original table and commit atomically. The newest policy is not a substitute for a missing historical one. A row without its rule needs an owner-supplied explanation or an unresolved status.

3. Observe: preserve history on success and refusal

AP-B3’s starter had a retry failure and two migration errors. The worker wrote examples, then a further probe exposed UNKNOWN_POLICY where the existing-ID contract required IDEMPOTENCY_CONFLICT. It repaired the supplied starter, passed ten development methods and eight additional probes. The failures identified missing behavior in the starter. Invoke your independent acceptance separately:

python3 companion/start.py check B3 \

Ten methods exercise retry after policy activation, changed-payload conflict, explicit reevaluation and parent identity, recorded-policy recomputation, persistence across restart, original payload spelling, protected history, evidenced migration, missing-provenance refusal, and the ASCII history boundary. Inspect record contents and row counts together. A response can be false even if no extra row was inserted: returning a newly computed answer under an old ID would misrepresent what that identity records.

For the missing-provenance case, compare database bytes before and after. For migration success, inspect both the retained old payload and the new record. For restart, distinguish reopening the same identified state from creating a fresh store at another path. An identical source file cannot compensate for a wrong state selection; B4 makes that failure explicit.

B3-P03

The existing request is resolved before choosing a policy for new work. Matching canonical input returns the recorded operation; an explicit new evaluation gets its own identity and parent link. This lets an operator inspect the old answer and the newly authorized answer without replacing either. A policy switch followed by restart is a useful challenge to the separation.

The actual AP-B3 operator passed all ten methods and the continuation on the same retained candidate. The original EUR 4,000 request remained a v1 STANDARD_QUEUE decision; explicit reevaluation under v2 returned HUMAN_REVIEW with the old request as parent. Retry returned REPLAYED without new rows. Both routes are correct for their identified operations; reusing the old ID cannot silently request the new evaluation.
