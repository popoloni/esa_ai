B2. Bound the provider and preserve attribution

Run commands from the package root. Live-client setup and current status · Offline recorded tours

Session planning target: setup 10 min · implementation 30 min · review and handoff 20 min (60 min total).

Delegate a bounded intake adapter around your repaired Treasury router. There are two distinct actors: your coding agent reads, edits and checks intake.py; the product’s injected Provider is a scripted local fixture. The latter classifies valid requests as MATCH or REVIEW; it is not the agent implementing the adapter. Invalid amounts are rejected locally.

A transient provider failure consumes an attempt; a response must belong to its request. Your result classifies requests without authorizing payment. The product fixture needs no network or paid provider. The live coding route uses the separately configured client described in the companion.

The new API is:

def evaluate_batch(requests, provider, *,
                   max_attempts=2, max_calls=4):
    ...

Each request supplies request_id and amount_eur. The injected provider takes those two values and returns exactly {"request_id": ..., "classification": ...}. Its classification is either MATCH or REVIEW. The local router’s outcome and the provider’s classification are distinct fields. Neither field is a payment approval, and the combined result keeps payment_authorized=False.

Write an example before coding. A batch contains an invalid negative amount, a valid item whose first provider call is unavailable, and two more valid items. With a total budget of three calls, decide which calls may occur, what the final item should report when the budget is exhausted, and what evidence a reviewer needs to attribute the response to its request. Count the failed attempt in the budget.

INTAKE/v1 distinguishes three ordinary record states. REJECTED means local validation prevented a provider call. CLASSIFIED means a valid, matching response was received. DEFERRED means the allowed work ended without such a response. Deferral is not a successful classification, and the implementation must not fill it with a default MATCH to keep the batch looking complete.

2. Delegate: retries are part of the contract

Only ProviderUnavailable is retryable. An unexpected exception remains visible. A response with another request’s identity, an unknown classification or a different field set raises ProviderProtocolError. Preserve request identity across every retry and report each attempt’s number and outcome. Duplicate request IDs in one batch are caller errors: validate the entire batch before any provider call. A duplicate therefore raises ValueError with calls=0, not after partial work. Errors retain their original type and expose receipt, attempts, records and calls. Keep preceding successes and the final INVALID_RESPONSE or PROVIDER_ERROR attempt. A raised exception must not erase consumed calls or make their later cost accounting disappear.

The limits have different scopes. max_attempts bounds each request; max_calls bounds the whole batch. A per-request loop can still overspend the batch budget if it resets the total count for every item. Conversely, checking the total only after a call permits one call beyond the approved limit. Derive your boundary examples from those two observations.

An invocation bound does not bound wall-clock time if the provider blocks forever inside one call. The contract deliberately describes a cooperative local adapter. An external untrusted process would require a separate execution boundary and a specific cancellation policy. Do not claim that a loop counter has supplied those properties. The companion runner’s process timeout is also a separate mechanism; it does not turn the intake function into a production network client.

Twelve methods challenge local rejection, attribution, identity-preserving retry, the global budget, response identity/shape and non-retryable exceptions. They retain preceding successes, provider ValueError, unavailability before malformed responses, and invalid attempts. Duplicate-ID refusal proves zero calls beside a valid unique-ID control. Protocol controls reject nonstring classifications with ProviderProtocolError and INVALID_RESPONSE, alongside valid MATCH/REVIEW. Trace each assertion to its obligation: correct shape does not compensate for a wrong request ID or unknown classification.

For the retry case, inspect the sequence of actual calls. For the global budget, count all attempts across all items. For an unexpected exception, verify that the adapter did not retry it. These observations matter more than a single “completed” label at the end of a batch.

B2-P01

The batch loop tries to finish an item already in progress after a transient provider interruption. It preserves the request identifier and records every invocation so the caller can see the effort spent before the batch returns. The completion path is designed to avoid abandoning useful work at the edge of an allowance. Review that path against both the item-level and batch-level budgets.

Artifact: evaluate_batch: the budget guard before the next provider invocation.

if len(attempts) > max_calls:
    break
event = {"request_id": key, "attempt": attempt}
attempts.append(event)

B2-P02

A classification is usable only when its response belongs to the submitted request and has the agreed shape. The adapter checks that relationship before adding a completed record. It distinguishes the retryable provider condition from other failures and retains the attempt evidence on exceptions. Invocation bounds and response validity remain separate decisions in the loop.

Artifact: evaluate_batch: response validation after recording the current attempt; exceptions retain the receipt.

B2-P03

Duplicate detection belongs before the first provider effect. This proposal examines the entire submitted batch before entering the existing bounded loop, so a late duplicate cannot invalidate work after calls have already occurred. It addresses identity within this batch only. A later process retry still needs the durable identity contract introduced in the history mission.

Artifact: Preflight helper called before the provider loop; error snapshots are attached by evaluate_batch.

def _unique_requests(requests):
    rows = list(requests)
    ids = [row["request_id"] for row in rows]
    if len(ids) != len(set(ids)):
        raise ValueError("duplicate request_id in this batch")
    return rows
requests = _unique_requests(requests)

4. Decide: hand off a bounded classification receipt

python3 companion/start.py continue B2 \
  --candidate work/b2 \
  --output work/evidence/b2-handoff.json

The continuation uses your retained module with a deterministic provider that fails once, then returns matching classifications. The batch includes a locally invalid request and a final valid item reached after the global budget is spent. It saves classification.json under work/evidence/b2-handoff/, containing the inputs, observed provider calls and result. The receipt identifies source bytes, protected dependencies, current tests and artifact hashes.

The actual AP-B2 operator independently passed all twelve methods and this continuation. Its three product calls were UNAVAILABLE, MATCH for the same request, then REVIEW for another. The invalid item consumed no call; the final valid item was DEFERRED. Read your complete sequence and explain its identities. These product attempts are neither coding-agent retries nor a model bill.

Finish the dossier with budget assumptions, the response contract, actual command receipts, the three proposal decisions, and the distinction between invocation count and elapsed time. A successful result is a local SCOPED_HANDOFF_READY. It does not prove provider availability or persistence across a process restart.

The next mission introduces durable decision identity and a policy history. B2’s provider attempt receipt remains useful evidence, but it is not automatically a durable business ledger. A continuation must say what is newly stored and what still belongs only to this batch observation.
