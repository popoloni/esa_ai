# B4. Find the selected state before repairing the code {#mission-b4}

**Session planning target:** setup 10 min · implementation 30 min · review and handoff 20 min (60 min total).

A Treasury process is running the expected source version, yet a new EUR 4,000
request enters the standard queue when the current rule requires human review.
One investigation proposes changing the threshold in code. Another finds that
the process selected a different ledger, initialized under v1. The same source
can produce different behavior because its state is different.

Your outcome is a read-only diagnosis, a bounded restoration and an explicit
reconciliation question. Use **Expect · Delegate · Observe · Decide (EDOD)**
with the supplied local incident fixtures.

## 2. Delegate: observation must not initialize the evidence

The diagnostic functions are:

```python
inspect_ledger(path)
diagnose(selected_path, expected_path,
         expected_policy="BR-001/v2", anchor_key="anchor")
recovery_plan(diagnosis)
```

`inspect_ledger` reads an existing file in read-only mode and verifies its
application and schema identity. It reports the selected path, digest, active
policy, decisions and audit count. A missing path is an error. Opening it with a
normal create-capable SQLite connection could manufacture the very state that
an investigation is supposed to observe.

`diagnose` compares the actual selected state with the expected binding and
identifies path, policy and anchor mismatches. It leaves both ledgers unchanged.
The fixture also contains an identical deterministic decision ID in both ledgers.
The ID is derived from matching record content; it does not prove that these files
have one historical lineage. Inspect the anchor and state binding rather than
claiming that a shared digest or decision ID makes the stores interchangeable.
