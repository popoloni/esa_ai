B4. Find the selected state before repairing the code

Run commands from the package root. Live-client setup and current status · Offline recorded tours

Session planning target: setup 10 min · implementation 30 min · review and handoff 20 min (60 min total).

A Treasury process is running the expected source version, yet a new EUR 4,000 request enters the standard queue when the current rule requires human review. One investigation proposes changing the threshold in code. Another finds that the process selected a different ledger, initialized under v1. The same source can produce different behavior because its state is different.

Your outcome is a read-only diagnosis, a bounded restoration and an explicit reconciliation question. Use Expect · Delegate · Observe · Decide (EDOD) with the supplied local incident fixtures.

1. Expect: identify code, state and the expected anchor

Continue B3:

python3 companion/start.py advance B4 \
  --from-candidate work/b3 \
  --dest work/b4

The command verifies the retained ledger implementation and carries its actual ledger.py and routing.py as protected dependencies. It creates incident.py for the new diagnostic. The accounting helper from G4 is supplied as a dependency; you can complete the Treasury route without having completed the Reservation route. For independent entry, choose this alternative:

python3 companion/start.py new B4 \
  --dest work/b4

Read docs/contract.md and observe the initial result:

python3 companion/start.py check B4 \
  --candidate work/b4 \
  --output work/evidence/b4-initial.json

OPS-B4/v2 identifies the expected state by its resolved path, history application ID, schema version 2, active policy and an owner-supplied historical anchor. The wrong ledger is a separate fixture opened by the same ledger implementation. The expected ledger has active BR-001/v2; the fresh wrong ledger defaults to v1 and lacks the anchor. Those are observable differences in state, independent of a source-code regression.

Write two competing hypotheses in DOSSIER.md: changed routing logic, and wrong state binding with unchanged logic. List the smallest read-only observations that would distinguish them. Include the resolved selected path, source digest, active policy, historical anchor and schema/application identity. A process name or a familiar filename is not sufficient evidence of which state was opened.

2. Delegate: observation must not initialize the evidence

The diagnostic functions are:

inspect_ledger(path)
diagnose(selected_path, expected_path,
         expected_policy="BR-001/v2", anchor_key="anchor")
recovery_plan(diagnosis)

inspect_ledger reads an existing file in read-only mode and verifies its application and schema identity. It reports the selected path, digest, active policy, decisions and audit count. A missing path is an error. Opening it with a normal create-capable SQLite connection could manufacture the very state that an investigation is supposed to observe.

diagnose compares the actual selected state with the expected binding and identifies path, policy and anchor mismatches. It leaves both ledgers unchanged. The fixture also contains an identical deterministic decision ID in both ledgers. The ID is derived from matching record content; it does not prove that these files have one historical lineage. Inspect the anchor and state binding rather than claiming that a shared digest or decision ID makes the stores interchangeable.

EDOD/1 work order mission_B4 — Persistent effect.

Expect — outcome: Diagnose the selected ledger and propose a bounded restoration. authority: Service operations lead, OPS-B4/v2 (teaching contract). acceptance: Compare actual and expected path, policy and anchor read-only; preserve both ledgers; leave reconciliation and production approval pending. The structured proposal includes restore_configuration_to with the resolved expected path; it does not perform or authorize restoration.

Delegate — editable_paths: incident.py, DOSSIER.md. protected_paths: docs/, tests/, READER_ENTRY.json, prior/, ledger.py, routing.py, operations.py. budget: 3 attempts / 30 implementation minutes; 30 s per check process; 0 external integration calls. stop_conditions: Missing ledger, changing evidence or requested record reconciliation. Protected inputs change or the declared attempt/time budget is spent.

Observe — checks: b4.check, b4.continue (commands below). receipt_fields: candidate_sha256_before, groups, inputs_unchanged, verification_progress, human_acceptance.

Decide — owner: Learner reviewer; Service operations lead for a changed rule. object: B4 candidate, identified bytes and its scoped handoff. allowed_decisions: ACCEPT, REJECT, ASK.

The structured proposal must include restore_configuration_to, the resolved expected path, with automatic_merge=False and production_authorized=False. Prepare and inspect the task before launch:

python3 companion/agent_session.py prepare B4 \
  --candidate work/b4 --output work/b4-agent
python3 companion/agent_session.py run \
  --session work/b4-agent --client claude \
  --max-budget-usd 5

Require the agent’s predictions before edits. Preserve the selected-state observations and stop it at an unsupported mapping or reconciliation decision. Its job produces diagnosis and a proposal; the operator owns continuation.

A recovery plan is not an executed recovery. The plan must name the expected binding, evidence to preserve and checks to run: historical replay, a current-policy probe on a disposable copy, and restart/state verification. It must leave record reconciliation pending. Which wrong-ledger records are valid work, conflicting retries or unrelated events is a different question from which file the service should use next.

3. Observe: distinguish wrong state from a false clean report

AP-B4’s first implementation passed six methods, but continuation requested an unspecified key and stopped. The operator retained that result, made the consumer field explicit in v2 and requested a bounded update. The worker reproduced the new missing-field case before adding the key and preserving its alias. This was clarified scope, not a retroactive implementation error. Your task starts with that explicit contract:

python3 companion/start.py check B4 \
  --candidate work/b4 \
  --output work/evidence/b4-first.json

Seven methods cover wrong-ledger diagnosis, shared-ID limitations, missing-file refusal, proposal authority, a clean positive control, failed-attempt accounting and the explicit consumer field. They compare original database bytes before and after diagnosis. The actual operator independently passed all seven after the agent’s bounded update.

The positive control matters. A diagnostic that always returns WRONG_LEDGER would detect the fault fixture but also reject the correctly bound store. A useful observation must discriminate the two. Similarly, an implementation that silently substitutes the expected path for the selected path can produce a reassuring report while never inspecting the actual fault.

Record a decision, its governing rule and the observation that could change it for each card.

B4-P01

Configuration provides a stable reference for interpreting an incident. This diagnostic builds its observations around that intended ledger and retains the path, policy and anchor comparisons in the report. It avoids mixing evidence from uncertain locations while producing the existing status shape. The review should establish that the reported observations identify the state the running service actually selected.

Artifact: diagnose: the two state observations used by all subsequent comparisons.

selected, expected = (
    inspect_ledger(expected_path), inspect_ledger(expected_path))

B4-P02

Restoring the expected binding leaves requests in the extra ledger that the intended store has never seen. Reconciliation would copy those missing identifiers into the intended ledger after diagnosis and restoration. That would retain work performed during the incident and present operators with one history. The attached recovery plan preserves the existing diagnostic while this additional behavior is proposed.

Artifact: recovery_plan: the currently supplied plan; the proposed merge is a separate requested change.

return {
    "restore_configuration_to": diagnosis["expected"]["path"],
    "preserve_ledgers": [
        diagnosis["selected"]["path"],
        diagnosis["expected"]["path"]],
    "verification": [
        "historical replay",
        "current-policy decision on disposable copy",
        "restart and state binding"],
    "automatic_merge": False,
    "reconciliation": "PENDING_OWNER_DECISION",
    "production_authorized": False}

B4-P03

Both selected paths are inspected read-only, and each observation carries its own state identity. The resulting plan preserves the ledgers while identifying the expected binding and the checks needed after an authorized restoration. Records created during the incident remain a separate reconciliation decision. Matching decision identifiers alone do not settle whether the same historical state was selected.

    inspect_ledger(selected_path), inspect_ledger(expected_path))
return {
    "status": (
        "WRONG_LEDGER" if issues else "EXPECTED_LEDGER_SELECTED"),

After recording all three judgments, reveal their checks and explanations together:

python3 companion/start.py review B4 \
  --candidate-ids B4-P01 B4-P02 B4-P03 \

4. Decide: restore the fixture binding and preserve the question

python3 companion/start.py continue B4 \
  --candidate work/b4 \
  --output work/evidence/b4-handoff.json

The continuation creates two clearly labeled ledgers using your retained ledger code. It records the wrong-state diagnosis and the recovery plan. It then restores only the local fixture’s selected_state.json binding to the expected ledger, observes the clean positive control, and runs historical replay plus a new v2 probe on verification_copy.sqlite. It reopens that disposable copy to confirm the new record survives restart. Both original ledgers remain byte-identical.

Inspect the artifacts under work/evidence/b4-handoff/:

Artifact Review question
diagnosis.json Which code and state were observed, and which mismatches support the diagnosis?
recovery_plan.json What binding is proposed, what must be preserved, and what is not authorized?
restoration.json Which local configuration changed, which checks ran on a copy, and what remained unchanged?
expected.sqlite, wrong.sqlite Which original evidence remains available for later reconciliation?
cost_report.json Were all included attempts counted, with a stated accepted-outcome denominator?

The actual AP-B4 v2 continuation executed this local restoration and retained both original ledgers unchanged. It kept production_authorized=False and reconciliation=PENDING_OWNER_DECISION. Those boundaries also govern your handoff; the fixture result does not resolve the wrong ledger’s records.

The cost report uses labeled illustrative inputs: a failed diagnosis, investigation and review, then fixture restoration checks. It includes all three in the numerator. Its one accepted outcome is a scenario assumption, not evidence that a human reviewer accepted your work or that an actual incident met its recovery objective. Your own economic claim needs observed costs, a defined acceptance unit and an appropriate comparison.

Finish the analytical dossier with selected state, expected binding, source version, observed policy, preserved evidence, restoration scope, unresolved reconciliation, next authorized check and the responsible owner. Add your three proposal judgments and what changed after observation. A reader should be able to distinguish “the fixture now selects the expected state” from “all consequences of the earlier state selection have been resolved.”

The completed Treasury chain carries your numerical repair, explicit text contract, bounded intake, preserved policy history and diagnosed state. Its identified candidates and scoped evidence still require a human decision about use.

Explain the decision

Why can the correct source produce the wrong current behavior? What could a create-capable database open conceal during diagnosis? Why does a matching decision ID fail to establish ledger lineage? Which observations support restoration, and which records still require reconciliation? Why are probes made on a copy?
